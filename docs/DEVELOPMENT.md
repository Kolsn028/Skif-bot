# Проверки и эксплуатация

## Локальные проверки

Из каталога `skif-bot/`, Python 3.12 (как в CI):

```bash
python -m pip install -r requirements.txt
python -m unittest discover -s tests
```

Один затронутый набор, например тиры:

```bash
python -m unittest discover -s tests -p 'test_tiers.py'
```

CI: `.github/workflows/skif-storage-check.yml` в корне репозитория. Он запускает полный unittest-набор для PR, затрагивающих проект. Перед изменением общего хранения, прав или жизненного цикла проверяйте полный набор. Для правок только документации достаточно проверки ссылок и соответствия исходникам; существующий CI может запускаться автоматически.

Не импортируйте main.py ради проверки: он запускает бота. Для ручных сценариев используйте отдельный тестовый токен и сервер; рабочий токен не копируйте в команды или отчёты.

## Данные

Рабочая база: переменная DATABASE_PATH, по умолчанию `data/skif-v9.db`.
Discord содержит сжатые JSON-снимки с проверкой целостности; текстовые логи служат для просмотра.
Автосохранение ограничено интервалом 60 секунд на сервер, неизменившиеся снимки пропускаются. /backup_now и штатное завершение обходят этот интервал.
При аварийном завершении несохранённые изменения могут потеряться; при недоступности Discord окно потери увеличивается. Это не непрерывный журнал транзакций.

Не проверяйте восстановление удалением рабочей базы: сначала сделайте /backup_now и убедитесь, что копия подтверждена.

## Хостинг (Railway или аналог)

Рекомендуемая конфигурация сервиса:
команда запуска `python main.py`, healthcheck `/health`, один экземпляр.
Перед запуском смонтируйте постоянный диск в /app/data — иначе SQLite
потеряется при перезапуске контейнера.
DISCORD_TOKEN и остальные значения храните в переменных сервиса.
Значения секретов в документацию не добавлять.

1. Убедитесь, что рабочее дерево/PR содержит только ожидаемые изменения, а CI завершился успешно.
2. Перед обновлением логики хранения убедитесь в наличии актуальной проверенной резервной копии.
3. Проверьте настройки сервиса и все ожидающие применения изменения окружения. Не применяйте чужие изменения вместе со своими.
4. Обновление main может вызвать автодеплой. Для документации, не требующей перезапуска, оставляйте отдельный PR до планового обновления.
5. После деплоя сопоставьте коммит, статус запуска и логи подключения к Discord. При восстановлении проверьте запись о восстановлении снимка и наличие ожидаемых данных. Healthcheck сам по себе не доказывает работу Discord-кнопок.
6. Для изменённого пользовательского сценария выполните безопасную ручную проверку на тестовом сервере.

Повторный деплой старого deployment может использовать его прежнюю конфигурацию. При изменении startCommand проверяйте, что новая конфигурация действительно применена в новом deployment.
Откат кода не равен откату данных: сначала проверьте совместимость схемы и снимков.

Документация и обычное обновление кода сами по себе не требуют повторного /setup. Эта команда меняет сервер; запускайте её только когда конкретное изменение требует настройки.
